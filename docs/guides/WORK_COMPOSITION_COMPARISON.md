# Individual Works and explicit composition

FLOW-14 keeps two or three explicitly selected compatible Works distinct. The
existing sequence is a manifest of Work references and a saved serial workflow;
each item retains its criteria, native sessions, candidate, admission and landing.
A completed first item never closes a failed or unstarted second item. The current
contract begins in one repository and does not promise an atomic multi-repository
transaction. Grouping does not merge native conversations or their prompt caches.

## Paired pilot and decision

The operator explicitly requested this comparison after green X4. One controlled
ledger project contained two dependent Works: normalize records, then summarize
the normalized values. A started the Works individually; B started one sequence.
Both used the same Git seed, source criteria, writable paths, immutable tests,
GPT-6.1 Sol medium native Responses connection and existing subscription. They
had independent roots, control graphs, native sessions and full journals. This
was one descriptive A-then-B pair, not the original eight-pair AB8 effect estimate
or four ordinary customer deliveries.

| Observed measure | A: individual Works | B: sequence |
| --- | ---: | ---: |
| Accepted, separately settled items | 2/2 | 2/2 |
| Recorded generation intents | 23 | 23 |
| Reported total tokens | 104,587 | 113,349 |
| Reported cache-read tokens | 0 | 0 |
| Active Work time, excluding navigation waits | 101.422 s | 103.750 s |
| Explicit public Start actions | 2 | 1 |
| Material correction after terminal delivery / rollback | 0 / 0 | 0 / 0 |

The sequence removed one explicit Start action. Calls did not decrease; B reported
8.4% more total tokens in this selected pair. Independent generations produced
slightly different valid patches, so token/time differences do not establish a
composition effect. Human context minutes, money, invoice charges, quota headroom
and physical HTTP attempt counts remain unknown. Local token-count estimates are
not extra generation calls. Returned usage was joined by explicit Work/session/
call IDs, not timestamps. Existing optional code review was not selected; the
same maintainer checks are not an independent-lineage audit.

Both public-TUI paths preserved a visible partial state: first Work DONE, second
NOT_DONE. Ten immutable unittest cases passed for each complete arm; normalization's
six checks also passed at its own settlement. The
offline replay applies each Work patch separately: normalization can pass while
the report remains unfinished, then the complete candidate passes. A refused
verifier-name attempt recovered by the agent remains part of measured cost; no
operator correction or coaching was used to finish a measured candidate.

Decision: retain explicit sequences for the operator's convenience and do not
enable automatic clustering or claim prompt/quota savings. This closes the
bounded paired comparison and its original per-item delivery criteria. An AB8
or larger ordinary-use cohort would be a separately bounded future experiment,
not a prerequisite or hidden follow-up required to use Work or sequence.

## Finite execution limits

The pilot preflight found a real defect: the TUI displayed finite calls/time
settings for SEQUENCE, but command construction dropped them and the sequence
CLI did not accept them. No comparison model call was sent before repairing it.
The existing CLI/config/dispatch/preparation ports now carry those settings.
There is no new scheduler, policy framework or collector service.

Use the TUI's **Execution options**, uncheck **Unlimited calls and time**, and
set the call/time values before starting **SEQUENCE · selected Works**. The CLI
equivalent includes `--max-model-calls 6 --max-seconds 180 --max-retries 0`.
These are separate limits for each Work's plan and implementation stages, as in
single-Work execution. Two Works with six calls per stage allow up to 24 such
calls; they do not share one six-call sequence quota. Optional independent code
reviews retain their separately selected route limits. Blank fields inherit the
profile/default; explicit CLI null removes that particular ceiling.

New sequences with explicit overrides use `tare.tools/work-sequence/2`; older
versions refuse this format before dispatch instead of ignoring its limits after
rollback. New readers retain old sequences and profile inheritance. The private
probe verified refusal by the installed 0.1.88 reader and zero-call replay by the
new reader. Missing v2 limits are refused before execution. The source-TUI pilot
used pre-release v1 states with explicit overrides, also supported by new readers.

Saved settings are reused on Resume; show, revision and resume cannot replace
them with new CLI limits. Running native sessions keep their exact deadlines,
identity, full history and cache affinity. Preparation with two slots receives
the same saved overrides. The pilot allowed six calls / 180 seconds per stage,
zero automatic retries and at most 48 data intents. It used 46, plus 16 calls for
the separate TUI implementation of the plumbing fix. Observed zero cache reads
do not mean the cache was reset or prove a future cache hit.

## Maintained evidence and retention

[The compact record](FLOW14_COMPARISON.json) contains the workload, input hashes,
per-Work patches, attributed cost/quality observations and limitations. Its 32 KiB
ceiling avoids keeping repository copies or raw prompts in source control.
`tests/test_flow14_comparison.py` replays both measured candidates and partial
obligations with Git and stdlib unittest, offline and without provider quota.
`tests/test_sequence_limits.py` covers literal CLI arguments, invalid limits,
legacy inheritance, revision/control, exhaustion, resume and parallel preparation.

The raw evidence of this run is not published. It was bounded to 64 MiB and
12 MiB per terminal trace and preserves original failures, native
journals, usage, source audits and cleanup receipts. Raw sessions/traces become
cleanup-eligible after 2026-11-19 once integration is green and no recovery needs
them. Only owned worktrees are parked. The compact workload, patches and tests
remain the durable destination; no recurring or automatic paid benchmark is added.
