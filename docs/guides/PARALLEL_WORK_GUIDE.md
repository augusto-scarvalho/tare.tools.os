# Parallel Work sequence: operator guide

Use this mode only for **two prepared, distinct Works** in the same project, with verification checks already attached to each Work in the graph. It overlaps *implementation preparation*, not admission. Review each Work's scope, prerequisites and checks first: both must be operationally ready, with known nonoverlapping writable target paths (including ancestor directories). Avoid a dependency between the two that would make the second unready. Declare any non-workspace resource used by a task or its checks in `metrics.shared_resources` (a list of nonempty strings); if the Works share a resource, use serial execution. For example, a shared database, external service, fixed port or global output directory is not isolated merely because the Git files differ. Only attest isolated effects when **both tasks and their checks affect their own isolated workspaces**; do not enable this for side effects you cannot rule out. Local model capacity is one slot; an optional pause for a human answer before each implementation also requires one slot.

## Start and inspect

In the console select the project and **Work sequence** (SEQUENCE) flow. Enter the two prepared Work IDs, comma-separated, in **Prepared Work IDs**; the sequence computes dependency order. For a new sequence check **New sequence: two isolated implementations**, then Start after reviewing the selection. The toggle requests two slots and confirms isolated effects; it is not an automatic isolation audit. The selected Works must belong to one project, and a new sequence saves its selection, model and settings. Inspect the saved sequence's status, per-Work notes and active Work before deciding to Resume. Do not confuse this with **Explore questions**, which runs independent research sessions rather than Work implementations.

Each preparation uses its own linked Git worktree at a frozen base and yields a scoped, hashed patch and an advisory proposal. Only ready Works with known, nonoverlapping target paths and no intersecting declared shared resources are paired; unknown/overlapping paths, shared resources, absent isolation confirmation or a single-slot local model fall back to serial execution. Preparation does **not** land a patch, settle a Work, or authorize it. The sequence incorporates prepared results **one Work at a time** against the current base. The Work execution owner still runs real verification and the ordinary audit/admission/landing path; a prepared proposal or a passing preparation is not a verification receipt or admission.

## Conflicts, cancellation and recovery

The saved preparation and proposal are retained on failure, conflict or cancellation; do not treat a conflict as automatically merged. Incorporation checks whether files changed since the prepared base and whether the import is valid. A conflicting proposal stays available for review while that Work is implemented serially on the current base. Cancellation stops further dispatch after the running work responds; earlier results and prepared artifacts remain in sequence custody. Inspect the sequence and active Work, resolve any underlying issue (scope, side effects, resource contention, changed Work/dependencies, verification failure or model availability), then Resume the saved sequence. Work runs already dispatched are reconciled through their own saved evidence; if contracts changed, review the sequence revision rather than silently reusing a stale proposal.

For capacity trouble or uncertainty, wait until active dispatch has stopped, check **Resume with one slot; keep prepared results**, and Resume. This reduces the saved sequence to one implementation slot without deleting existing prepared results; compatible prepared results can still be checked and incorporated serially. A plain Resume reuses the **saved** selection, deployment and isolation settings, not newly edited new-sequence toggles. To run serial from the outset, leave the new-sequence toggle off; with an existing sequence use the one-slot Resume option. If checks or incorporation fail, inspect the recorded reason and Work receipts, fix the concrete cause and Resume or deliberately revise the remaining Works; never claim a proposal was admitted just because it was saved.

## Measure before claiming benefit

Compare a serial baseline and a two-slot run of comparable Works using **end-to-end delivery latency**: from selection/start through preparation, serial incorporation, real verification, audit/admission and final settlement of both Works. Record each Work's completion and retry/conflict/cancellation time, plus total model calls/tokens and compute/runtime usage (including duplicated preparation and verification), not only the `parallel_waves.elapsed_ms` preparation window. Record differing model capacity, workload and resource contention. Report observed results with those conditions; parallel preparation may cost more or take longer, and no speedup or usage saving is guaranteed without measurement.
