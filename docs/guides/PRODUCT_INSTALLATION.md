# Install, update and roll back

The bundle contains the five tare.tools packages, all dependencies as wheels,
`requirements.lock`, the source commits and hashes, and a Python installer.
On Windows, use 64-bit Python 3.12: the `win32` bundles are built with it.
On Windows, the bundle includes MinGit with a native BusyBox shell for
non-interactive commands, with a pinned version and SHA-256 and every file in the manifest.
The launcher puts this Git only on the release's PATH and does not change the machine's Git.
Git Bash/MSYS and extensions such as Perl are not part of this execution contract;
the native shell avoids the MSYS incompatibility with MXC confinement.
You do not need to clone the ecosystem or reach a package index during installation.

Extract the bundle into a folder and run, in that folder:

```powershell
python install.py install .
& "$env:LOCALAPPDATA/tare.tools/product/tare.cmd" console --root C:/my-project
```

To use plain `tare` in any Windows terminal, run this once in the checkout:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/ops/install_product_tasks.ps1 -CommandOnly
```

Open a new terminal. The command uses the managed installation, with automatic
updates, and takes precedence over an old development `tare.exe`.
PATH points to the fixed launcher in `product`, not to a release: each
launch follows the active version, including after an auto-update or rollback.
This mode changes only the user PATH; it does not register or restart services.
The full task setup also configures this command.

```powershell
cd C:/projects/my-project
tare
# Or, from any folder:
tare C:/projects/my-project
tare "C:/projects/project with spaces"
```

`tare` opens the current folder; an explicit path can be absolute, `./relative`,
`../other` or `~`. The folder must exist. Use `./status` for a folder whose name
matches a subcommand. `tare status` still shows the installation.
On Linux/macOS, put the directory of the `tare` launcher on your shell's PATH.

`RUN_TUI.bat` opens this same installation. A source install (see the README)
runs `tare` from the clone instead. **Settings · F2** shows the version actually loaded
and says whether it is a release or development.

To install in another folder, use `python install.py --home C:/tare install .`.
The launcher is then `C:/tare/tare.cmd`; set `TARE_PRODUCT_HOME=C:/tare`
to use `RUN_TUI.bat` as well. Prefer short paths on Windows.

## Authenticate and complete a task

Choose a model in the TUI. You can import your own profiles with
`tare.cmd profiles import my-model C:/profiles/model.json`. Each entry point has
its own profiles: the installation uses `product/state/profiles`; a source install
uses `.reconciliation/profiles` next to the clone, or `profiles` under `TARE_STORAGE_ROOT`.

On startup, the TUI looks for the Claude, Codex and AGY CLIs (PATH and default install folders) and adds the models of each one it finds to the picker, without spending a model call.
It asks each CLI locally whether it is signed in; one that is installed but not signed in appears in a warning with the command that signs it in. Existing profiles you wrote or edited are never replaced. `TARE_CLI_DISCOVERY=0` turns the search off.
In **Settings → Connection details → Authenticate**, enter the key for the selected
profile. It goes to the operating system's vault and stays available
across versions. **Check** queries the endpoint when the protocol offers that
check; saving a key does not confirm access. CLI profiles keep using the
provider's own login. An environment variable that is already set takes
precedence over the vault; the TUI tells you so before saving.

Send the task, then review the changed files and the result in the TUI. History
lives in `product/state`, separate from the execution environments. `TARE_STORAGE_ROOT`
selects an existing history folder, including to keep using the history of an
earlier unmanaged installation.
In that case, also pass the original control root when opening:
`tare.cmd console --os-root C:/original-root --root C:/my-project`.
The combination of project and control root identifies legacy conversations;
selecting only its storage folder does not change that identity.

In the managed installation, that identity stays in `product/control`,
independent of the active version. Use the `tare.cmd` launcher generated by the installer;
the command setup above keeps an old `tare.exe` on PATH from opening the previous installation.

## Check the installed version

Query the state of the managed installation through the launcher:

```powershell
& "$env:LOCALAPPDATA/tare.tools/product/tare.cmd" status
```

The output shows `current`, `previous` and the versions and commits of the five
packages actually selected for new launches. Read this output to learn
the state of this machine. The file
`docs/operations/PRODUCT_RELEASE_INPUTS_WIN312_2026-09-27_0.1.63.json`
preserves the inputs of the historical 0.1.63 release.

## Update or roll back

To use the new version in the TUI, reopen it after the update:

```powershell
& "$env:LOCALAPPDATA/tare.tools/product/tare.cmd" update C:/downloads/new-bundle
& "$env:LOCALAPPDATA/tare.tools/product/tare.cmd" status
& "$env:LOCALAPPDATA/tare.tools/product/tare.cmd" rollback
```

The update installs offline into a separate environment, checks hashes,
dependencies and imports, and only then switches the active version. A failure keeps the
previous version. Reinstalling the same bundle does not erase the rollback
point. `rollback` switches between the two retained versions without reinstalling packages,
deleting profiles or undoing project files. Reopen the TUI after the switch.
Releases that change persisted formats must keep reading the old format
to offer the same rollback; the installer does not convert user data.

## I2I-06 bounded qualification

The [executable model of the current transition](PRODUCT_TRANSITION_MODEL.md) declares
limits, recovery assumptions, negative controls and offline tests of the
real persistence/Serve cut points. It complements I2I-04/05; it does not promise simultaneous
migration of processes, directory durability under power loss or
automatic recovery under permanent failure.

## I2I-01 transition contract

`active.json` is the authority **for new launches** through the managed launcher.
Until the transition is sealed, `current` keeps pointing to N. The successor is
prepared side by side: verification of the bundle and its identity, installation
without a package index, `pip check`, imports and writing `ready.json`. Before activation,
the installer verifies again the bundle, the installed Python, the
`ready.json.bundle` identity and the dependencies. `rollback` also qualifies the target
before switching the pointer.

Under the existing installation lock, a single atomic replacement of
`active.json` publishes `current`, `previous` and `last_transition` together. The temporary
file is written, flushed and synced before `os.replace`.
Qualification, sync or replacement failures before the seal do not
rewrite the bytes of the previous pointer. This is not a transaction over the whole
installation: a prepared candidate or bootstrap files may remain
after a failure. Directory durability against power loss is not promised.

Format of the last receipt (the IDs below are illustrative; they are full SHA-256 hashes of
`bundle.json`, not package versions):

```json
{
  "current": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
  "previous": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "last_transition": {
    "from": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "to": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
    "operation": "update",
    "at_utc": "2026-10-16T12:00:00Z",
    "qualification": "releases/bbbbbbbbbbbbbbbb/ready.json"
  }
}
```

`operation` is `install` on the first activation (`from` and `previous` null),
`update` on a switch by installation and `rollback` on a rollback. `at_utc` is the local UTC
clock, with one-second precision; it is not a global ordering.
`qualification` is a reference, relative to the installation root, to the
target's `ready.json`, whose content is `{"bundle": "<full SHA-256>"}`.
The receipt is local and unsigned, and keeps only the last switch: it is not an audit
log, nor proof of provenance or of the health of processes already running.
`status` shows it with the pointer. Reinstalling the already active bundle preserves the
pointer bytes, including the receipt and the rollback point. Legacy pointers
without `last_transition` stay valid; only an actual switch adds a receipt.

Rollback swaps `current` and `previous` and replaces the last receipt; an incomplete
target, a mismatched identity or a missing previous version blocks the switch.
`prune` keeps the two referenced versions also when there is a receipt, without changing
`active.json`; other versions that the system does not allow to be renamed are left for
a later attempt. This is not the same as tracking every live process.

TUIs and Serve processes already started may keep running on N: the switch neither revokes nor migrates
them. The existing Serve restart policy is separate from the seal;
activation does not mean that every process runs the same version.
I2I-01 does not cover: global freeze, new concurrency protocols,
canaries, data migration, consensus or the additional guarantees of I2I-02.
Compatibility of persisted data remains the release's responsibility.

### I2I-04: observe an exact rotation without running it

The `product.py` bootstrap (also shipped as `install.py`) offers
`transition-status`: read-only, with no write lock, update, recovery,
new processes or replay of Work/tools. PowerShell example, using **the same
absolute home and the same bootstrap** before and after the authorized transition:

```powershell
$productHome = "$env:LOCALAPPDATA/tare.tools/product"
$productPython = 'C:/path/to/python.exe'
$productBootstrap = "$productHome/product.py"
& $productPython -I $productBootstrap --home $productHome transition-status
# Record current=N, previous and server.release/installation/pid; keep the output.
# The owner separately runs the already authorized N -> N+1 update.
& $productPython -I $productBootstrap --home $productHome transition-status
```

Keep both outputs outside the product and compare the full SHA-256 IDs of the
exact subject: N before, N+1 after and previous=N. Do not infer identity from names
or versions. `completed=true` / `qualified_rotation_complete` requires a last
`update` receipt for the pair, a PASS trial catalog pinned by digest, in the `canary` phase, with
`selected=candidate`, incumbent=N and candidate=N+1, ready.bundle=N+1 and
protocol-1 health from the same installation on N+1,
with no pending drain/stop. Each file and health response is limited to 64 KiB.
The pointer is reread after the observation: `pointer_changed` discards the combination;
`pointer_recheck_failed` preserves the uncertainty. This is not a transactional snapshot nor
cryptographic proof against a malicious local writer.

`reasons` contains stable codes, for example `catalog_trial_missing`,
`catalog_digest_mismatch`, `catalog_trial_mismatch`, `ready_identity_mismatch`,
`receipt_pair_mismatch`, `evidence_path_invalid`, `evidence_missing`,
`evidence_malformed`, `evidence_oversized`, `evidence_io_error`,
`health_unavailable`, `server_identity_mismatch`, `incumbent_still_serving` and
`server_not_settled`. `serve` separates selected/incumbent/foreign_or_legacy/unknown;
an active pointer or a healthy server without a pinned trial is not enough. Initial
installation, explicit rollback and automatic rollback appear as `initial_install`,
`rollback` and `auto_rollback`, never as a qualified rotation.

**Sole managed Serve** means the single active incumbent of the managed endpoint,
identified by installation/release/PID; it does not mean every process on the
machine. Old TUIs may stay open on N and are not a second
update authority. The command does not enumerate listeners or prove the absence
of other servers; the maintainer qualifies that exclusivity separately.
I2I-01/02 still own selection/drain/recovery, and I2I-03 owns the trial.

The status does not prove data preservation or the migration of every process.
The real authorized rotation, before/after hashes of the selected durable custody files
and reopening through the public TUI are separate maintainer evidence,
not a result invented by a unit fixture. The original issue26 roadmap asks for
an exact production transition authorized by the owner, an exact receipt, a single active
incumbent and a retained rollback; it does not add distributed consensus.

This command must exist in the bootstrap used to observe. On the first
update that introduces it, record `tare status` and the Serve health beforehand;
use `transition-status` after the update. The receipts of updater N remain
the proof of the qualification before activation.

### I2I-05: bounded observation of two independent installations

`python -B scripts/ops/qualify_product_cohort.py packet.json` (or `-` for stdin)
writes only JSON to stdout. The function `qualify(packet)` accepts a dict, a JSON string
or UTF-8 bytes. Limits: 256 KiB, 16 nodes/observations, 32 packages and labels of up to
128 characters. The local ID keeps the current format of 64 lowercase hex characters; that
format does not make it global or authenticated. Duplicate JSON keys are rejected.
There is no SSH, scheduler, update, rollback, provider or file writing.
Use `-B` so that loading the modules in your own tools does not create bytecode.

Exact format of the v1 envelope (metavariables below, not real evidence):

```text
{
  "schema": "tare.tools/product-cohort/1",
  "expected_nodes": ["LAPTOP-01", "WORKSTATION-01"],
  "expected_sources": {"<name of each package>": "<full Git commit, 40 lowercase hex>"},
  "observations": [
    {
      "node": "<a declared node>",
      "installation": "<expected local hash, 64 lowercase hex>",
      "status": <whole object from the public status output>,
      "transition_status": <whole object from the public transition-status output>
    }
  ]
}
```

Declare every expected package, not only those that responded. Each status
contains `current`, `previous` (distinct full SHA-256 hashes), `packages` with
`name`, `version`, `commit`, and an update `last_transition` with exact from/to and qualification.
The catalog_trial reference needs the full candidate path and SHA-256
digest; the local canary proof remains I2I-04's job.
The transition-status requires schema `/1`, completed as boolean true,
reasons exactly `["qualified_rotation_complete"]`, serve selected, the same
pair, and server with release=current, installation equal to the declared ID and
a positive integer PID (the local observer already checked the protocol, and it is
not exported in server). Other public fields
are tolerated; they do not replace the required bindings. The checker reuses the
public I2I-04 qualification; it does not revalidate trial files through the supplied JSON.

Results: `authority=NONE`, `observation=PASS|PARTIAL|REJECTED`, bounded global
reasons and `nodes` with node, installation, observation and bounded reasons.
PASS requires every declared node to qualify and no envelope error;
PARTIAL keeps each PASS sibling even when a node is missing, unreachable, duplicated or
divergent; with no success the result is REJECTED. Omitting an observation stands for an
unreachable node; an object without status/transition_status does not qualify either.
Labels that differ only in case do not count twice. Invalid
declarations reject the envelope; extra observations block a global PASS.
Exit codes: 0 PASS, 1 PARTIAL, 2 REJECTED.

LAPTOP-01 and WORKSTATION-01 have the **same local installation hash**, because the
local path the protocol uses is the same. The hash does not identify a machine globally:
the observation key is the declared node plus the opaque local ID. Equal local IDs and
bundles for different platforms are allowed if the full set of
package inputs is identical to the declared one. Do not change the protocol/ID.
Supplied labels and JSON do not prove remote authenticity or freshness. Honest
collection through the existing authenticated SSH, custody and confirmation of the exact subject
remain the maintainer's responsibility after review; offline fixtures are not
real observations of the nodes.

`notify(peers)` only asks each machine's updater to run. `updates_started`
true means the request was accepted, **not that the rotation completed**. OS failures, a timeout
(60 s per request) or a nonzero return each stay false independently, with no retry
or explicit process termination, and they do not skip the next peers. Each node
keeps its own locks, receipts and recovery; the protected pipeline does not change. There is no
consensus, global lock, new remote execution, fleet state or authorization
issued by the observation. Reconcile evidence with the existing canonical owner;
do not create another authority or repeat effects.

## I2I-02 managed transition

Manual install/update/rollback and the whole automatic operation use the same
`install.lock`: concurrent runs fail without entering; the system lock is released
when the process exits. Before each switch, the captured current/previous pair
is checked again. Qualification before the seal does not change the pointer.

The update first reconciles the already selected version with Serve. A pending
reconciliation blocks downloading another candidate. Replay after activation only tries
to finish that transition, without repeating tools or Work. There is no freeze
or TUI migration; data compatibility remains the release's job.

The restart uses `/health` and `POST /control/drain`, bearer `tare-local`, protocol 1,
the exact pid+release+installation identity (SHA-256 of normcase(resolve(home))) and an
owner UUID. The 120-second lease is renewed while work finishes;
the Serve fence blocks new requests. Only the same owner, with
busy=0, can stop the server. The port must close before the
`Tare-Serve` task starts. No taskkill, task termination or listener search is used.
A legacy server, a foreign identity or a busy port without managed health postpone
the operation with a diagnostic. The busy deadline releases the lease; a communication
failure on release lets the lease expire. The Task Scheduler adapter is
Windows-only; the logic can also be exercised on Linux with a fixture adapter.
With no managed task and no server or busy port, the update proceeds
normally and reports `no serve task`. A selected Serve in drain postpones the
search for another candidate.

If B does not start, A (previous) is validated and selected atomically with an
`auto_rollback` receipt. A must also respond with the exact installation and release.
If that fails, the command exits nonzero and keeps A selected. Replay recovers A
without switching back to B. A safety postponement does not authorize killing processes
or switching to another candidate. The receipt alone does not prove health.
If the rollback was a manual choice, a failure to start that version keeps the
choice and exits with an error; it does not undo the operator's rollback.

`active.json` keeps only the last `auto_update` policy, with `paused` and `after`,
next to the last receipt. A manual rollback pauses new versions. To clear the pause and
the barrier, without inventing an activation receipt, run:

```powershell
tare auto-update --resume
```

This command only clears the policy; the next automatic run reconciles and
looks for candidates. Auto rollback writes `after=B` (full SHA-256 ID), excluding
B and earlier publications. A later C may proceed. The search is limited to the 30 most
recent publications and the 10 most recent candidates with CI: a missing boundary does not
allow inferring order or a downgrade. Reinstalling the active bundle preserves the bytes
of the pointer, receipt and policy. There is no journal, database, unbounded history or
data migration. Safe control requires protocol 1 in the participating versions;
a legacy server needs a supervised transition for that generation.

## Shadow and canary before promotion (I2I-03)

A managed update now has a bounded qualification of the model discovery
protocol. After preparing and validating the N+1 bundle, an installer
with I2I-03 support starts N and N+1 in two disposable processes, on private
loopback ports. It uses each release's real handler with an embedded profile,
a random bearer, and empty, separate state and settings. These endpoints
accept only `GET /v1/models`; POSTs, chats and tools are refused.
No conversations are copied and no inference runs.

First, shadow compares one response from each version. Then ten requests
of **generated qualification traffic** are distributed deterministically:
eight to N and two to N+1 (20%). Each N+1 response is compared with a fresh
N response; together with the shadow, that is up to 14 HTTP attempts. The comparator
validates the catalog structure and the preservation of previous IDs and owners.
Added models and valid context-window changes are allowed.
This does not evaluate the quality of model responses.

The default limit is zero candidate errors: the first failure stops the canary,
selects N and blocks promotion. A failure in the N reference itself is
`INCONCLUSIVE`; no success and no evidence against N+1 is invented. There is a shared
30-second deadline, up to three seconds per GET and responses of up to 64 KiB.
The probe's own processes are terminated and awaited; cleanup waits up to five
seconds before killing the same process. On Windows, the probe uses the base
Python with `-I -S` and the packages of the verified release to control the real PID,
without confusing it with the venv redirector.
Both platforms pass an explicit `-B` and attest in the handshake that bytecode is
disabled, which also preserves the installation's code caches.

Only `PASS` allows swapping the bootstrap and sealing `active.json`. The activation
receipt references `releases/<id>/catalog-trial.json` and its SHA-256. The file
`last-catalog-trial.json` in the installation keeps the last attempt, including
refusals, with IDs, counters and hashes; it does not keep payloads, prompts or keys.
These data feed the transition diagnostic and the next rotation
decision, without a collector or a growing history.

On automatic update, a rejection reuses `auto_update.after` so that the same
publication is not downloaded and tried again. Current, previous and the last
activation receipt are preserved; `prune` removes the discarded preparation and
keeps the protected releases. `INCONCLUSIVE` does not condemn the publication.
`tare auto-update --resume` keeps the existing mechanism for clearing the barrier.
Manual rollback and recovery from failures after the seal still go through I2I-02.
Reinstalling the already active bundle does not repeat the trial or replace its receipts.

This contract covers the product catalog and qualification traffic. It does not
reproduce ordinary traffic, tools, data migration or gradual routing of chats.
An updater older than I2I-03 keeps using its earlier contract to install this
first version; the prior qualification applies to updates run by the new updater.
This prepares a first concrete rotation in I2I-04 without claiming that a general
rotation is already done.

When dogfooding through ConPTY, send select/delete/paste as separate keyboard
actions and check the displayed numeric value before starting the agent. Grouping them
in a single write can change the effective limit.

## Build a bundle

Use the build environment and the exact revisions from the release inputs file:

```powershell
python scripts/ops/build_native_release.py --lock inputs.json --roots roots.json --output build
python scripts/ops/pack_native_release.py --release build --output bundle
```

The first command exports the bytes of full commits, excludes local changes
and requires identical wheels from two builds. The second resolves the dependencies
once and preserves their bytes and hashes. Keep the full bundle to repeat
the installation; resolving the dependencies again on another date may pick
different versions. Hashes detect changes; they do not authenticate the provenance
of a bundle received from third parties. Bundles are per platform: build the Linux one on
Linux itself. Windows and Linux (Ubuntu/WSL2) with Python 3.12 were verified;
other systems need their own bundles and validation.

Prerequisites: Python 3.12 with `venv` (on Ubuntu, `sudo apt install python3.12-venv`)

## Automatic updates

Maintainers publish releases: every push that changes `main` in one of the five repositories can become a
release. CI publishes it ([ADR-074](../adr/ADR-074_PRODUCT_RELEASES_FROM_CI.md)): when tare.tools CI passes on
`main`, `.github/workflows/release.yml` runs `python scripts/ops/publish_product.py` on a GitHub-hosted Windows
runner for the commit CI tested. It builds the bundle from fresh mirrors of the five repositories (never a
development checkout), tests the installation in a disposable folder and publishes the GitHub release
`product-<id>` with `bundle.zip` and `published.json` (the heads it was built from, which the next run compares
with); its notes end with `CI passed on main: <run>`. The workflow attests the bundle's build provenance: check a
download with `gh attestation verify bundle.zip -R augusto-scarvalho/tare.tools.os`. Outside GitHub Actions the
publisher publishes nothing unless given `--here`, and then only a draft: that machine has no signing key, and
installed copies ignore a release without a signature. Sign the draft with the recovery key and publish it with the
commands at the top of `scripts/ops/release_signing_key.py`.

The release is signed ([ADR-075](../adr/ADR-075_SIGNED_PRODUCT_RELEASES.md)). The workflow creates it as a draft;
a separate job that alone holds the project's Ed25519 signing key signs the bundle, checks the signature and only
then uploads `bundle.zip.sig` and publishes the draft. The signature covers `tare.tools product bundle` and a newline
followed by the SHA-256 of `bundle.zip` in hex. Check a download by hand from the extracted bundle with
`python install.py verify-signature bundle.zip bundle.zip.sig`, or from a checkout with
`python relay/native_product.py verify-signature bundle.zip bundle.zip.sig`; neither needs an installation, and the
exit code is 0 when the signature is valid. `--key HEX` (repeatable) checks against other public keys instead of the
ones built in. Installed copies require the signature: the updater takes only releases that have a `bundle.zip.sig`
asset, downloads it with the bundle and verifies it against the built-in keys before extracting anything. A bundle
whose signature is missing or does not verify is not installed: `auto-update` reports `refused` with the tag, leaves
the installation as it was and tries again on a later run, so a release repaired by hand with the recovery key still
installs.

On each machine, the `Tare-Update` task runs `tare.cmd auto-update` at logon and every 5 minutes. It reads the
public releases over HTTPS (one GitHub API call, two when the installed release is older than the newest hundred; no
login and no GitHub CLI), takes the newest signed release (one with `bundle.zip.sig`) whose notes say CI passed and
that is newer than the installed one, downloads its `bundle.zip` and verifies the signature. It installs the new
release next to the current one and uses the
I2I-02 transition described above to reconcile Serve safely. The TUI is never
closed: it warns once that an update is installed, and the next launch
already uses the new version; conversations continue where they stopped.
