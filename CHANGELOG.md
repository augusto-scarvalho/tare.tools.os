# Changelog

Notable changes to `tare.tools.os` are recorded here, newest first.

## Unreleased

- The retry question after an audit stop says what a yes allows: "Let this task go on correcting?", with corrections continuing while the audit finds new defects and stopping again on a repeated defect or 6 refusals in a row. It asked for "one more attempt", and a yes ran three correction rounds (about 48 minutes).
- The kernel pin moves to 08851e4: a read with `start_column: 1` returns a page instead of one line, so an implementer that fills that default (DeepSeek did) no longer stalls into a NO_PROGRESS stop.
- The side agent sees when an implementer attempt stopped without changing anything (`implementation_stop`, such as NO_PROGRESS): it read three identical refused attempts and called the coordinator's "stopped without progress" wrong.
- The consent judge takes an affirmative that says how to carry the work out as allow: "pode tentar de novo, corrigindo esses dois pontos" (yes, fixing those two points) was judged unclear at 0.82, because the options called any added detail a change, and the coordinator asked again for a plain yes or no. The options now call unclear only consent that waits on something still to happen or changes the scope, duration or saving of what was asked, so "only for this session" or "only the docs folder" still ask again.
- The side agent reads whether a delivery's files were applied: the implement step it sees carries the delivery's file scope ("unapplied candidate, not project files"), which it dropped before, so after an audit stop it wrote that the changes "remain applied" while the project was unchanged.
- A TUI opened with `--coordinator` shows that coordinator before the first message: the launch banner names it, the header and the model picker read it instead of the saved model preference (Qwen3.8 Low while Gemini 3.8 would run), and Check probes it. The banner names roles that share one pin once and takes a third line, so six pins no longer end at "implementer:".
- Coverage progress counts only reads of code and references: the packet tare builds for the auditor (request and diff) is rebuilt for every continuation, so rereading it at other lines no longer counts as reading something new and keeping the chain going.
- The side agent's reasoning level is the owner's: `heads_up_effort` in the routing policy (routing.json) applies to its writer routes, as `planner_effort` and `auditor_effort` do for theirs; unset, each route keeps its own default. Saving routes (/routes) keeps the owner's reasoning levels instead of dropping them.
- An audit reuses the project's satellite inventory while its submodule pins stay the same: building the candidate tree keeps it, and the review, its continuations and cached-decision lookups read it instead of listing every satellite object again; a moved pin reads it anew. Each implement on the OS repository paid seconds for this, even when the audit decision was cached.
- A coverage continuation counts as progress only when its session read something (a file or range) that no earlier review of its chain had read, taken from its journal; the auditor's list of what remains is no longer the measure. Comparing that list's text let a reworded item pass as progress, so the chain might never stop by itself. Continuations recorded with the list measure end the chain.
- An audit finding whose claim is identical (case and spacing aside) to one of the previous refused audit of the same unit counts as repeated even when the auditor did not mark it, so the delivery stops and asks instead of paying for another correction. The auditor's own mark is never removed and nothing fuzzy is compared; the ledger keeps claim digests, and a run recorded before this change only starts the comparison.
- The heads-up tells the user's queued messages from the host's by the session's operator inbox, which keeps every message the user queued, instead of by the shape of a message id: a message queued with any id (tare native) counts, and a host message with a uuid-like id does not.
- A refused model request says why: the kernel pin moves to ad897e4, which keeps a 4xx reply's error type and message without request headers or keys, and the turn's result, its failure lines ("Provider said: ...") and an audit's result carry it to the user and the coordinator. An HTTP 400 showed only its code.
- An HTTP model request whose cleanup was unconfirmed is recoverable in the TUI that made it, once the HTTP worker the kernel recorded for it is gone; the user no longer has to close and reopen tare. A process that took a recorded PID later (created after the owner's invocation started, or after a worker's invocation ended) no longer counts as that process still running. A worker the kernel left without a PID still needs its owner to end.
- A coverage continuation counts as progress when it settles at least one obligation its predecessor left unread, even if its reading found as many new ones; the chain stops at the first continuation that settles none. Counting the list stopped a continuation that read two files and found two more.
- A delivery recovered from its unit receipt (an interrupted turn or a lost task record) keeps the files its audit requires outside the plan, so the next plan must still include them. Recovery dropped them, the old plan ran again, and the refusal guard stopped the delivery with a question instead of a replan.
- The TUI heads-up reads every message the user sent during the turn: the typed request replaces only the turn's opening message, and messages queued while it ran (Enter queue) follow as later messages; the host's own messages (consent choices, recoveries) stay out. The typed request replaced them all, and a side agent called a requirement the user had queued invented.
- A turn whose delivery was not applied ends with the host's line "[tare] Not applied: the project files are unchanged" (and whether the candidate is preserved), after the coordinator's reply. A local coordinator had summarized an unapplied candidate as "what changed", and nothing in the reply said otherwise.
- A re-audit honors the instance's `--auditor` pin: a retry or recovery of an earlier audit whose route the pin now excludes starts afresh with the pinned auditor. It reused the failed audit's route, the pin refused it before any inference, and the coordinator reported the old HTTP 400 as the API failing again.
- Repeated audit refusals stop a delivery only when the audit reports a defect again after a correction (the auditor marks that finding `repeated`), or after 6 refusals in a row as a cost backstop. Three refusals in a row stopped it and asked the user whether to retry even when each audit found a new, real defect (5 questions in one demand). Runs recorded before this change keep the three-refusal rule.
- A plan's scope grows when the independent audit proves a file outside it must change: each audit finding may name the files to change (`paths`), the delivery returns those outside the plan as `missing_target_paths` with a planner repair, and the next plan must include them before the implementer runs on the preserved candidate; the user still approves the new files. The planner kept returning the same plan and the coordinator asked the user to open another block, which then hit the overlap guard.
- An incomplete audit keeps continuing, one continuation per user turn, while each continuation leaves fewer unread obligations than it started with (`<review>-coverage`, `-coverage-2`, ...); the chain stops at the first continuation that reads nothing more. After one incomplete continuation, every "continue" returned the same saved result for good, and only a changed candidate got past it.
- The interrupted-model recovery tests use the receipt the kernel actually records (`transport: isolated_stdlib_http`), with a regression case on a receipt left by a coordinator that died mid-request.
- The satellite snapshot tests copy their fixture repositories with symlinks kept as links, so the dangling-link scenario runs where Git checks out real symlinks (CI) as it does elsewhere.
- Check receipts keep their usual "$ <check> (exit <code>)" blocks first; the per-file statuses (a file cut by the cap, one that could not start, files not run) follow them and survive clipping.
- A plan's Python tests run one file per check (`pytest-tests:<file>`), each within the 300-second cap, instead of every file in one 300-second run. Plans with several heavy suites ended INCONCLUSIVE without a finding; a single file over the cap is still cut and named. The guard's key and the verification contract do not change, and a check asked for by test path is answered with the per-file names to run.
- The independent auditor can read the satellites a change depends on: a candidate snapshot fills the project's initialized submodules at their pinned commits from local objects, with a fixed number of git processes and no network; a submodule that cannot be filled is marked unavailable instead of failing the candidate; without local pins the auditor gets the running paired runtime packages as read-only references, and only then a named gap. Audits of changes that depend on kernel records ended INCONCLUSIVE because satellites/ was empty in the candidate.
- The consent dialog works more than once per conversation: a choice reaches the coordinator as a host-prefixed message with its own id, the same repeatable path as the pending-consent re-ask, instead of Runtime's one-time host observation. The second dialog choice in a conversation failed with "native continuation conflicting observation" and every later resume failed the same way; conversations already in that state resume.
- An update no longer removes the release a running TUI or `tare serve` still uses: the launcher records its process for the release it starts from, and cleanup skips a release with a live record, or, for one started before this change, with a running process inside its folder; when that cannot be known, the release stays. Windows let the folder be renamed under running processes, so the release was half deleted and an open TUI lost its checks and its coordinator mid-turn.
- A conversation whose coordinator died during an HTTP model request resumes: Resume or the user's next message abandons that request when its owner is proven gone (the owner PID recorded for the invocation is not alive, or, for an invocation recorded before this change, the resume holds the session's writer lock and the invocation has ended). It stayed stuck with LOCAL_CLEANUP_UNCONFIRMED. CLI requests still need their own cleanup proof, since a child process can outlive its owner.
- A plan revised in the same user turn runs its implementer in that turn: each attempt records the plan it ran, and an inconclusive delivery no longer blocks a different plan. The user had to send another message only to run the plan the coordinator had just saved; repeating the same plan unchanged is still refused.
- The consent judge understands one-word answers in any language: it is told that a bare affirmative means allow and a bare negative means deny, its options are plain language, and an allow decides at 0.8 (a deny still needs 0.9). A plain "pode" or "ok" kept the folder or retry question pending before; no refusal or condition in the measured sample reached 0.45 (docs/history/JEV_CONSENT_QUALIFICATION_2026-11-07.md). No word list is consulted before the judge.
- A yes to "allow one more attempt?" belongs to the task, not to one plan: it survives a plan revision and is still spent by a single attempt. The question was bound to the plan's hash, paths and contract, so revising the plan right after the user said yes asked the same question again. Scope changes stay covered by the task's file permission.
- The independent auditor's call budget grows with the change it reviews: 8 calls plus one per two changed files and per 400 diff lines, up to 24, still within the conversation's remaining calls. A fixed 8 left a 17-file change INCONCLUSIVE for incomplete coverage three rounds in a row, each costing the user another message.
- Kernel pin moves to 8c4a639: on the Anthropic Messages API the last call of a budget no longer forces the delivery tool while thinking may be active (the API rejects it with HTTP 400). Audits through claude-api-opus-5-5 failed on their 8th call; they now finish.
- An implementer that waited for folder consent resumes with the calls and time the conversation can fund now, for that invocation, without rewriting its saved budget. One started in a conversation's first turn has an unbounded budget, and later turns have a finite call ceiling, so the old check refused every resume (R5) and the demand could only move in a new conversation. A conversation without the minimum for an implementer is still refused, with a message that says what is available and what is required.
- Correcting or revising an applied change starts from the project with a fresh implementer: the applied record stays as the barrier against older work, instead of being dropped. Without it, an earlier unapplied candidate (a cancelled attempt from before the application) came back, and the host asked the planner to cover its files over and over.
- The pending-consent re-ask tells the coordinator, in English, to ask for a plain yes or no; it is a host instruction, and the coordinator already answers in the user's language.
- Without a consent judge (no Jev key and no idle local judge), folder access and the retry question say "Reply yes (sim, pode, ok) to allow it; any other reply declines it" and read the reply that way, as before the judge. They asked for a natural reply that only a short yes could satisfy, so a natural yes or a no kept the question pending and the coordinator asked again without end, with no way out in `tare serve`. The question records which rule it announced, and the reply is read by that rule.
- Folder access and the retry after repeated failures are decided by what the user means, in any language, instead of a short list of yes words: in the TUI the question opens an Allow/Deny dialog (Deny focused, so a stray Enter declines), and a typed reply, in the TUI or `tare serve`, goes to an isolated closed-choice judge (hosted Jev first, the local judge only when Jev is unavailable) that sees the host's own question and the user's words, never the coordinator's context or its stated reason. It decides only at 0.9 or more; any other reply keeps the question pending, without spending it, and the coordinator asks again. With no judge, only the short yes still allows. A dialog choice resumes the conversation by itself, telling the coordinator through a host observation, never a synthetic user message.
- A stop after repeated failures is lifted by the user's plain yes in the conversation, not only by `/retry_delivery`: when the stop fires, the host records a pending question and the coordinator asks the user in plain words whether to try again; if the user's next message is a short yes (the folder-consent reader), the next implement passes the stop once. The host reads the user's own words from the journal (never the model's, nor a host observation of changed files); no new message, or any other reply, keeps the stop.
- `/retry_delivery` also works on a planned demand that has no candidate yet: it starts a fresh implementer with the user's authorization, which passes the repeated-failure stops. A demand that the overlapping-scope stop refused before any implementer ran (a new request on the same files later in the conversation) could otherwise never go on, since the command required a retained candidate.
- A waiting worker resumes without its folder only after the user's reply declined it: the reply is recorded in the asking session (TUI and `tare serve`), instead of a refusal being inferred from a missing pending request. A coordinator that skipped the question could have told the worker the user said no; now the worker keeps waiting and the coordinator is told to ask.
- A coordinator can no longer escape the repeated-failure stop by opening another demand: before an implementer starts, a unit whose target files overlap another unapplied unit of the conversation that reached the stop is refused too, and the refusal says the way on is the user's `/retry_delivery`. Dogfooding the file deletion, the local coordinator opened two demands with the same goal after the stop, and their fresh ledger entries let them through. `tests/test_candidate_checks.py`'s fixture repository sets `core.autocrlf`, so its line-ending assertion no longer depends on the machine's Git configuration.
- The end-to-end deletion test that once failed only inside tare's sandboxed checks (`explicit_regular_scratch_directory_required`) no longer reproduces: measured inside the check, its scratch folder and every parent are regular directories and all four cases pass. On a failure it now names the scratch root and what `is_dir`/`is_symlink`/`is_junction` report for it and each parent. `tests/test_command_protection.py` compares the recorded verifier executable after `os.path.normcase`, since on Windows `python.EXE` and `python.exe` are the same file and the check sandbox records the resolved name.
- A retained candidate that never edits the generated disposition manifest is requalified when only the project's copy of the manifest moved under it: its patch still applies and fresh checks and review run against the project as it is. Before, only a candidate whose patch carried the manifest could be requalified, so any later manifest regeneration in the project left the demand refusing to deliver ("The project changed since the retained candidate"), however often it was replanned.
- The stop after three audit refusals counts only the auditor's refusals: a candidate the audit accepted and the host then refused to apply (a dependency or the project changed) no longer counts, so fixing that cause and delivering again works. Dogfooding, two accepted candidates refused for the manifest's line endings had stopped the demand.
- The disposition manifest checks out with LF on every platform (`.gitattributes`), as its generator writes it. On a Windows checkout it had CRLF, the candidate check regenerated it with LF, and the host then refused to apply any audited change whose auditor had read it ("An observed audit dependency changed before application").
- A worker waiting for a folder no longer holds its demand: once the user's reply grants nothing it resumes without the folder (told so, no wait credited), and a new plan releases it for a fresh implementer. Dogfooding the TUI, a declined folder request left every later implement refused ("the waiting worker still needs the user's read permission", then "the waiting worker, plan or project changed"), and the coordinator could only suggest granting the folder or a new conversation. An unanswered request still holds the worker.
- An independent audit can accept a change that only deletes files: with no changed file left in the candidate to read, the review diff that shows the deletion is the evidence it cites. Dogfooding the file deletion with the local Qwen implementer, Opus accepted the deletion of an unused module on the diff and the host turned it inconclusive, because it requires citing a changed candidate file. A change that also edits files still needs one cited.
- A file a native implementer deletes stays a deletion through candidate revision, application and review (an empty file included), instead of failing as an edit without an after-image; the TUI's activity and the heads-up's step detail tell a requested deletion from a completed one. The kernel pin moves to `bd9e0a4` (tare.tools.kernel #4), whose `restore_bytes` recreates a deleted file, so undoing a turn that deleted one brings it back.
- The kernel pin moves to `40ac307` (tare.tools.kernel #3): a native implementer can delete a file with `edit(delete=true, changes=[], sha256=<current>)`, the only deletion, and boolean tool arguments accept the text `"true"`/`"false"` that Qwen's call format sends.
- A user's correction of a change tare already applied plans in a round of its own: the demand's three planning delegations guard one request against loops, not every later correction. Dogfooding the TUI on the kernel's file deletion, two corrections had used the round and a planner's invalid scope (a test directory named as a file) took the third, so the CI fix outside the saved plan could not be planned and the coordinator suggested a new conversation. A correction of a refused candidate stays in the same round.
- The heads-up writer sees what the TUI's user does not: for each delegated `implement`, what it was asked (`note`), what the implementer reported and what its independent audit found (verdict and findings); before, it read only that the call succeeded. Its prompt says the user sees only the final reply and the step names, puts first a claim the record contradicts and a choice whose consequence the reply hides, and makes one exception to the rule against notes about the process: a check the reply claims (tested, verified, passes) that the steps show failed, never ran or ran before later edits, unless earlier steps were left out. On the dogfood turn whose 7 candidates the audit refused while the reply said "89 tests pass", the note now says the audit never accepted a candidate and that earlier rounds found code defects. On the 18 labeled notes it is within one run's noise of the previous prompt: a fresh run of each kept 7 and 9 of the 14 wanted notes and wrote 2 and 3 of the 4 unwanted ones, and a rerun of the same prompt loses about a third of the wanted notes, so prompts are compared on several runs or on dogfood labels, not on one run of these 18.
- `ci_suite.py merge` now selects the newest evidence per shard when a CI run is partially rerun: the result job downloads all attempts of every shard for its platform (broad `pattern: ci-<platform>-*`, `merge-multiple: false`), and merge picks the highest `(attempt, retry)` folder for each shard — numeric comparison (attempt 10 beats attempt 2), `-retry` wins within the same attempt, and ties are broken by absolute path string. A shard whose newest attempt is red, unfinished or invalid fails the merge; it is never silently replaced by an older green attempt. Only the winning folder for each shard contributes to the plan, verdict, test maps and measured seconds.
- tare stops handing a unit back to the implementer after the independent audit refused its last 3 candidates, as it already did after 2 failed checks: the coordinator tells the user what the latest audit found and asks how to go on. Dogfooding the TUI, a finding the local implementer could not fix (a file its tools cannot delete) kept it and the auditor going for 7 rounds and 65 minutes.
- The node's lease tests wait for a child's or grandchild's PID file to hold its number, not only to exist: the process creates the file before writing it, and `test_escaped_grandchild_after_root_exit_gets_reaped` read it empty (`int('')`) on PR #17's node job.
- A challenger's workspace is found through `read_run()`, which rides out the moment a Windows reader is denied while the worker replaces `run.json`; `challenger_workspace.tree()` read it directly and failed `test_native_session_automatically_runs_one_isolated_challenger` on a Windows CI shard.
- `scripts/ops/run_focused_tests.py` keeps its logs, JUnit and receipt in a new folder under `temporary-evidence/`, which Git ignores, unless `--output` names another, and refuses a folder Git would commit. Dogfooding the TUI, a planner read `--output <new-evidence-folder>` in `AGENTS.md` as a folder in the change: the implementer's candidate carried the receipts into the commit and, after a new test, edited them to match instead of rerunning. `AGENTS.md` now says they are receipts of one run, never committed or edited.
- The test that a message receipt keeps the conversation's scroll no longer fails on a slow runner: it scrolls home at once instead of after the next refresh, which a slow Windows runner reached only after reading the old position.
- The TUI keeps each heads-up note it showed with its turn (the request's end, the reply's start) in the conversation's `heads-up.json`, and its log rows name the conversation, so notes met while dogfooding can be labeled by a person: `scripts/heads_up_calibration.py notes --since <ISO time>` lists them.
- Heads-up notes lose Jev's note gate and no longer stop mid-word. The user labeled 18 notes by the consequence writer: they wanted 14, including all 4 written on turns where Claude Code's side agent had said nothing, and the gate ranked the 18 worse than chance (AUC 0.41), dropping 6 of the 14 wanted, all 3 its regex caught among them. A note over 500 characters is now cut after its last whole sentence.
- Heads-up notes call the writer about a third as often, after a review of the funnel against Claude Code's side-agent notes:
  - A note is about the conversation more often than the turn it follows, and no count of a turn, nor any question hosted Jev answers about one, tells well whether a note will follow: the filter's AUC is 0.61 on sessions it was not fitted on, not 0.68. So the writer now runs when the score reaches 0.25 (a busy turn) or on every fourth turn since it last ran, reading that whole window: the skipped turns' steps (kept with the conversation's pace) and tare's facts over them, besides the earlier exchanges. On the labeled turns that is 32% of turns instead of 77%, and 98% of the noted ones fall in some run's window. Little is lost: on 49 noted turns Sonnet raised the side agent's concern on 2 reading the turn alone and on at most 2 reading the window, so the writer, not the pace, limits what is found; the 10% sample is gone, since the cadence's turns measure what the score misses.
  - Jev's rating of each turn, logged only, is gone: it added nothing to the score.
  - The writer reads what the work did, from what tare already recorded, instead of only where: each edit's old and new text, a demand's objective and criteria, what explorers were asked and found, delegated reports and commands' last output. tare's process facts (a failed test, an edit after the last test) no longer reach it, and its prompt asks what follows from the change (a license, a platform or version rule, git history, a quota) and rules out notes about the process. On 69 labeled turns its notes turned from process to consequences, at about the same rate: Jev's note gate passes 11 of 18, against 3 of 24 before, and no note on a quiet turn argues from what the record does not show, against 3 of 5. It still raises the side agent's own point as rarely (one partial match on the 47 noted turns read while changing it, one on the 2 never read), so whether the new notes help waits for labels from use. Each call reads about twice the record (median 34 kB).
  - Jev now judges the written note instead (`GATE`): where what it judges is in the state, it separates the notes users accepted from the cheap writers' process notes with an AUC of 0.93, and a regex catches notes that argue from what the record does not show. It only logs what it would drop until labels from use confirm the cut.
  - `scripts/heads_up_calibration.py claude` without `--writer` now spends nothing: it measures the score and the cadence on every labeled turn, by session, counts a turn a continued session repeats once, and prints the weights a refit gives. The judge-question and brief experiments are removed, their ceiling measured.
- Heads-up notes (`relay/heads_up.py`), in the TUI, `tare serve` and `tare-copilot`. After a finished turn, a side writer tells the user the one thing to know before relying on what was just done or said: a measurement whose setup differs from what will run, a cost to come, a changed default or a broken promise, a rule that can catch too much, a silent failure.
  - It runs as a funnel. Code counts what the turn did (edits, tests, failures, facts tare checks itself, the size of the request and reply), and a logistic score over those counts decides which turns reach the writer.
  - The writer is the routing policy's new `heads_up` role: Sonnet 5.5, then Sol, with Haiku standing in; /routes changes it. It reads the conversation before the turn as well and writes one note or none.
  - Hosted Jev drops a note the reply already says, and it rates every turn in the log only, without deciding.
  - The TUI shows the note, and `/heads-up` puts it in the composer as a question to the agent. `tare serve` hands it to the session's next turn, and tare-copilot's note reaches the model through VS Code's history.
  - The feature is on by default; the TUI option turns it off for the machine, and `TARE_HEADS_UP=off` turns it off for one process.
  - Every decision is logged in `<storage>/serve/heads-up.jsonl` with scores, probabilities, routes and times, never the texts. A tenth of the filtered turns still reach the writer, and `/heads-up` logs that its note was used.
  - How it was chosen: Claude Code transcripts hold the notes users accepted from its side agent. On 249 such turns (49 noted), the counts separated noted turns from quiet ones with an AUC of 0.68 cross-validated, while Jev's questions, asked as TypeSafe advises, added nothing (0.66 with them, 0.64 at best alone). Haiku, Luna and the local model flagged process details as often on quiet turns as on noted ones, while Sonnet wrote consequence notes on 31% of the noted turns and 22% of the quiet ones.
  - `scripts/heads_up_calibration.py` repeats these measurements: `claude` judges questions, briefs or writers against the accepted notes, `replay` sends saved tare sessions through the funnel, and `report` reads the log in use.
- Backlog item `product-update-verify-attestation-20261104`: installed copies should check a release's build attestation (or at least the CI run its notes cite) before installing it; today any release whose notes say `CI passed on main` is taken.
- SPEC-OS-SHIP-001 AC-21 and the backlog item `ship-workflow-trust-20261104`: Ship's preflight flags workflows that publish or deploy while trusting code they should not (`workflow_run` jobs that do not require a `push` run of the same repository or check out the triggering commit, `pull_request_target` jobs that check out the pull request's head), refusing a pull request that adds one and reporting one already on the default branch.
- CI builds and publishes the product releases (ADR-074): `.github/workflows/release.yml` runs `publish_product.py` on a GitHub-hosted Windows runner when tare.tools CI passes on `main`, for the commit CI tested (`--commit`), and attests the bundle's build provenance. Each release carries `published.json`, which the next run reads (`--state-from-release`) to tell whether anything packaged changed. Outside GitHub Actions the publisher publishes nothing unless given `--here`, so the maintainers' scheduled task stops by itself.
- The release workflow trusts only this repository's `main` (ADR-074): `workflow_run` also fires after a pull request's CI, a fork's included, so it publishes only after a `push` run of this repository and always runs `main`'s publisher, never the triggering run's code; `ci_passed` counts only `push` runs, and a commit older than the newest release's is never published.
- Auto-update works for anyone, without the GitHub CLI or a login: it reads the public releases over HTTPS (one API call per check, within the 60 an hour GitHub allows unauthenticated) and downloads `bundle.zip` from its public link. The CI check moves to the publisher, which releases a bundle only after tare.tools CI passed on `main` for its OS commit and says so in the notes; an installed copy takes only such releases. An installation older than the newest hundred releases finds its own by name instead of never updating.
- The isolation sweep creates the folder its pytest runs use as `--basetemp` parent: pytest creates `--basetemp` only inside an existing folder, so the first sweep on main failed every run at setup.
- A manual CI run with the `isolation` input looks for tests that pass only by luck of order or company: each shard runs every one of its test files alone, then all of them in a shuffled order seeded by the run id (`scripts/ci_suite.py isolate`), and reports what failed, without touching the test map.
- `test_streamed_reply_redraws_only_its_tail_and_reads_the_same_as_one_message` flushes the live reply before reading it: the 80 ms flush timer had not ticked after the last block on a loaded Linux runner, so the sampled view missed it.
- `test_powershell_read_host_with_live_display` waits up to 60 s for the PowerShell prompt and 30 s for the answer, each with its own ceiling, under a 120 s test limit: a cold `powershell.exe` on a loaded hosted Windows runner missed the shared 10 s. The loops still end as soon as the text appears (1.7 s locally).
- The test session imports the kernel's Codex client module before any test replaces `NativeHttpClient`: imported for the first time under such a patch, `CodexHttpClient` inherited from a stand-in function and failed, so `test_work_parallel` broke whenever no earlier test in its shard had imported the module (it fails alone, too).
- ADR-073 supersedes ADR-068 with the branch practice the repositories follow: `main` everywhere (tare.tools.local-labs renamed `master`), changes through pull requests from short-lived branches, no required `dev`, merged branches deleted by GitHub. The locality guide links tare.tools.local-labs on `main`.
- ADR-072 and SPEC-OS-SHIP-001 decide Ship, delegated delivery through remote CI/CD: `tare ci` generalized to any GitHub repository, an alert and shepherd lifecycle that ends with its subject, an identity and protection preflight, rule-based triage with receipts, `.tare/ship.toml` for what GitHub cannot tell, a fix loop through ordinary Work, and after-merge watching without deployment. Ten `ship-*` backlog items carry it; the decisions index now lists ADR-071 and ADR-072.
- CI runs each platform in shards on separate runners, 4 on Linux and 6 on Windows: `scripts/ci_suite.py slice` gives each shard a share of the plan's test files balanced by their measured seconds, and `Tests (linux)` / `Tests (windows)` merge the shards into one verdict, the test map and the seconds (`ci_suite.py merge`). The full regression drops from about 28 (Linux) and 38 (Windows) minutes on one runner to about 7 per shard; required checks keep their names.
- The rename dialog tests that check a finished save wait for the save worker before asserting: the save runs in a worker thread, and one UI pause was not enough on a slower runner (`test_ui_rename_write_failure_ui_unchanged` saw the dialog still saving on the hosted Windows runner).
- The node service workflow describes the platform suites it complements without calling them self-hosted.
- CI runs on GitHub-hosted Linux and Windows runners (`Tests (linux)`, `Tests (windows)`) instead of the maintainer's self-hosted ones: the satellites check out over HTTPS on both platforms (no deploy keys), Python comes from `actions/setup-python` with a pip cache, and the test map that focused runs read moves from the runner's tool cache to the Actions cache. The repository variables `CI_RUNNER_LINUX` and `CI_RUNNER_WINDOWS` move it to your own runners, and pull requests from forks then skip it. README and the CI feedback guide say so.
