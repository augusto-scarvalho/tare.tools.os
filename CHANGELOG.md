# Changelog

Notable changes to `tare.tools.os` are recorded here, newest first.

## Unreleased

- With `--local_only`, tare now implements only where the project's checks run in the sandbox, which today means an Action review chosen in `/permissions` (Edit + system commands). Before, a local-only conversation in a project without one planned, implemented and then ran the model-written checks directly on this machine, as you, with network access and your whole disk. Now it refuses before any implementer starts, and before it plans a delivery, so you do not approve a plan that cannot be implemented: "Local-only mode implements only where this project's checks run in the sandbox; here they would run directly on this machine. Choose an Action review in /permissions (Edit + system commands), then ask again. No implementer started." This covers every way of starting an implementer: a new attempt, `recheck_candidate`, `/retry_delivery`, a waiting worker, `/session` tasks, Work runs and resumed sessions. Off Windows, where there is no sandbox, local-only mode does not implement at all. A plan-only request still plans, and `/permissions` says which applies in local-only mode. Other modes are unchanged. This is an interim guard; the coming change that runs checks in the sandbox by default replaces it with the general rule.
- `/permissions` and `/tools` no longer list the terminal for the main conversation. Its coordinator and the workers it starts never get the terminal; only `/session` tasks and `tare agent --terminal` do. For the main chat the panel now says `System commands: Not in this chat: its coordinator and workers do not get the terminal. /session tasks do: …`, without `terminal_*` among its tools; a `/session` task keeps `Terminal on this machine, not sandboxed, not reviewed`, and a view that cannot tell says the terminal is for `/session` tasks and `tare agent --terminal` only. In `tare serve`, `/yolo` no longer promises "a terminal": no serve session ever had one. It now says what it does: edit files as `/accept-edits` does and find a turn's changes for the audit from a snapshot of the whole project. `/yolo default` also says that the TUI's `/session` tasks then get the unsandboxed terminal unless an Action review is set. Only text changed; the guides and the VS Code Copilot guide say the same.
- A local model no longer gets the terminal of **Edit + system commands** without an Action review, in `--local_only` or when a session's model is local in any other mode. That terminal runs commands directly on your machine as you, with network access and your files and credentials in reach, with no sandbox and no review. Such a session (a `/session` task or `tare agent --terminal` on a local model, or a provider switch onto one) now runs without the terminal tools, still reads and edits within its write scope, and its first reply and the model say why and that an Action review in `/permissions` gives sandboxed commands. A session saved with the terminal cannot be resumed on a local model: start a new conversation or continue it on a cloud or CLI model. Hosted models keep the terminal as before. `/permissions` and the Tools panel now call it what it is: `System commands: Terminal on this machine, not sandboxed, not reviewed` (or `None for a local model`), the Action review choice that turns it on reads **None: terminal on this machine, no sandbox**, the warning under it says so plainly, and each such command shows as **Unsandboxed command** in the activity. The guides say the same.
- A pytest check that fails in the Windows sandbox only because the sandbox would not let it read a secret file (a test that loads the project's `.env`, for example) is now reported as inconclusive, `ISOLATION_SECRET_DENIED`, instead of failing tests that look like broken code: tare says the sandbox does not let commands read secret files such as `.env`, so those tests cannot be judged there, that the model must not copy the secret elsewhere, rename it or change the tests to hide this, and that you decide whether such a check may run outside the sandbox. Every failure of the check must be a permission error on a file or folder the sandbox denies by name (or a refused network connection, as before): one assertion failure, a permission error on an ordinary file, or output that is not pytest's keeps the check failing.
- The gap named at the end of the next entry is closed: a protected command can no longer reach a nested secret by renaming or moving a folder above it. While a protected command's session or check runs, tare keeps each secret that lies below an editable folder open (it does not read it), and Windows then refuses to rename or move any folder above it, whatever tool tries. What you will notice: during that time you cannot rename, move or delete those folders yourself either (with the whole project editable, `services` and `services/api` for `services/api/.env`); editing, renaming or deleting the secret itself and everything else in those folders still works, and the folders are free again when the session or check ends. If tare cannot open one of those secrets (it was removed a moment earlier, for example), protected commands are refused with a message naming it, instead of running without that protection.
- A protected command on Windows (Tare MXC) can no longer read a secret anywhere in your project. Before, only a `.git`, `.codex` or `.aws` at the project's top level was always denied, and `.env`, `.ssh`, `.npmrc` and `.pypirc` only there and only with the Jev or local judge; a `services/api/.env` was readable by any protected command, and so by the model through its output. Now, whatever reviews the command, `.env` and `.env.*` files (`.env.example`, `.sample`, `.template`, `.dist` and `.defaults` stay readable), `.ssh`, `.aws`, `.codex`, `.npmrc`, `.pypirc`, `.netrc`, `.git-credentials`, `.pgpass`, `.gnupg`, `.kube`, `.azure` and `.docker/config.json` are denied at any depth of the project and of the folders granted to it, and so are nested Git folders wherever the top-level one already was. A program that opens one gets `Permission denied`, so a test that reads `.env` now fails inside the sandbox and is reported as a failing check. tare looks for them when the command's sandbox starts (dependencies, virtual environments and caches are skipped), so a secret created afterwards is not covered. The sandbox can deny at most 32 paths: a project with more, or too large to search (100,000 files and folders or 32 levels), now refuses protected commands with a message that says how many it found and that you can move secrets out of the project or open a smaller folder, instead of leaving some readable. Names stay visible in folder listings, and a command written to get around the rule can still read a nested secret by renaming a folder above it that it may edit; the command's review remains the guard against that.
- With `--local_only`, a local audit that does not cleanly accept no longer stops the change for good. When the local auditor answered ACCEPT while still listing open items, tare used to throw the whole review away as a model failure (two of three audits in a real run), so the conversation never reached **Apply this change?**. On that same-family local-only audit only, tare now reads such an answer as not accepted: as a revision when it lists findings (the implementer corrects them, as usual), otherwise as open items. It keeps the auditor's summary, findings and items and starts the summary with "tare read this review as not accepted: the auditor answered ACCEPT while listing open findings or remaining items." When that audit leaves only open items (no findings) and the checks passed, **Apply this change?** now also appears. It says the auditor did **not** accept, lists the items (up to 10, as plain text) and starts on **Do not apply**. **Apply anyway** applies the change as your decision: the result records it so (`user_decision`) and never calls it audited or accepted. Hosted auditors, audits outside `--local_only` and runs without a TUI are unchanged: there an ACCEPT with open items is still an invalid delivery, and nothing is applied without an accepted audit.
- With `--local_only` a conversation can now plan, implement, check and audit a change on the local model alone. Before, it read files and then stopped with "No configured planner with at least high reasoning", because local models could only coordinate and implement. In that mode, and only there, the local Qwen3.8 model now also plans and audits: your choice of the mode, not a claim about its quality. It plans at `xhigh`, its lowest level at or above the planner's high minimum (a planner with no explicit level now always takes that lowest level, as the planner picker already did). It audits at `xhigh` too, the local level nearest above the usual high. Because it is the implementer's own model family, its audit is not independent: the review, its receipt and the delivery result say **same-family audit, not independent**, and before applying the change tare asks **Apply this change?**, with the files and the audit's summary; **Do not apply** leaves the candidate unapplied, and while the question is open the turn's time stops. Where nobody can answer (`tare serve`, headless runs, Work runs) the change is not applied, as before: "No independent auditor is available." When no local planner is available, tare now says so instead of blaming reasoning. `tare models --role planner|auditor --local_only` lists the local model, and `--planner ninfer/qwen38-gsq@xhigh` and `--auditor ninfer/qwen38-gsq@xhigh` work with `--local_only`. In every mode `tare models --role implementer` now lists the local model that automatic routing already used as implementer, and `--implementer ninfer/qwen38-gsq@low` works. Other modes, `--prefer_local` included, keep hosted planners and auditors and the independence rule unchanged.
- A pytest check that fails in the Windows sandbox only because the sandbox refused its network connections (a test that starts a server on 127.0.0.1 and connects to it, for example) is now reported as inconclusive, `ISOLATION_NETWORK_DENIED`: tare says the sandbox denied a network connection on this machine and that those tests cannot be judged there, instead of reporting failing tests and asking for a fix of code that may be correct. Every failure of the check must be such a refusal: one assertion failure, a file error of the test's own, or output that is not pytest's keeps the check failing. Like a timeout, an inconclusive check of the session does not block a change whose own checks pass, which is then applied only when its unit's tests cover every changed file.
- Async Python tests now run in the Windows sandbox of protected commands and checks. The sandbox blocks loopback networking, so Python could not create its `asyncio` event loop there and such tests hung until their timeout, reported as inconclusive. Python started by a protected command now gets a `socket.socketpair` that works without loopback, so `asyncio.run`, thread wake-ups, `asyncio` subprocesses and async pytest tests pass; the sandbox's network stays closed, the host's own loopback services included. Still failing there: tests that open real TCP or UDP servers on 127.0.0.1, Python started with `-I`, `-E` or `-S`, libraries that build their own loopback connections (Twisted's select reactor, ZeroMQ), and any async Python when your Windows profile folder (`C:\Users\<name>`) has a name longer than about 11 characters: the socket's path would not fit, and the command's error output then says so.
- Links in a `tare serve` or Copilot request, `/research` in `tare serve` (the links you give, the links found on those pages and free-search results) and the sources of a research flow are now read like `read_url`: only public web addresses, in a separate reader process that checks every connection and redirect. `localhost`, your local network, your Tailscale machines and cloud metadata addresses are refused even when you typed the URL yourself, so these paths can no longer read your own dev server (`http://localhost:3000`). A refused link shows `✗ tare reads only public web addresses` in the progress line, and a refused research-flow source is listed as `REFUSED`. Each page now starts its own reader (about two seconds on a laptop) and stops after 30 seconds, and these reads no longer go through a system proxy.
- The model button test no longer fails at random on CI: while it waited for the button to be laid out, the console's own header could relabel the button with the machine's model. The test now keeps the header quiet for its duration. No product behaviour changed.
- The side effect named in the next entry is gone: the Backlog satellite is now pinned at `086f02e`, whose link check no longer asks the drive root (a drive root cannot be a link), so saving a graph (`--save`) from inside a protected command works again.
- A protected command on Windows (Tare MXC) could list the names and sizes of the files in any folder of the drive, your home folder included, and return them to the model (it could not read their contents). It no longer can: it lists only the project, its runtimes and its scratch folders, plus the few system folders Windows opens to every sandboxed app, such as Program Files. One side effect: a Backlog command that saves the graph (`--save`) from inside a protected command now stops with `Access is denied: 'C:\\'`, because Backlog checks every folder of the path, the drive root included, for links; reading the graph still works.
- `read_url`, and tare's own reading of the pages a researcher cites, now reach only public web addresses. A model (or a page it read) can no longer make tare open `localhost`, your local network, your Tailscale machines (`100.64.0.0/10`) or a cloud metadata address such as `169.254.169.254`: those addresses, in any notation, and names such as `localhost` or ones ending in `.local`, `.internal` or `.ts.net` are refused before any network call, and the reader checks every connection it opens, so a redirect or a name that resolves to a private address is refused too. The model gets a refusal saying only public web addresses can be read, and nothing is cached. Reading your own dev server (`http://localhost:3000`) through `read_url` is refused as well, and these reads no longer go through a system proxy.
- The known gap below is closed: with `--local_only`, a protected command that the local judge cannot review (it reviews only while it is already loaded and idle) no longer runs unasked in **Edit + system commands**. The first such command of a turn asks **Run commands without review this turn?**, showing that command; **Run without review this turn** runs it and the turn's later commands the judge cannot review without asking again, and **Deny** refuses only that command, so the next one asks again. The yes lasts for that turn only (the implementer's commands and the host checks alike); a new turn, a resumed worker or another console asks again. Each such command is marked as not reviewed in its activity row (while it runs and in its recorded details), in its review record and in its receipt (`review_status: not_reviewed_this_turn`, `classifier: local_unavailable`). Outside YOLO tare still asks about each command, and `--disable_judge` in YOLO still runs without asking. `/permissions` now names the local judge in local-only mode and says what happens when it is not available; the guides and the `--local_only` help say the same.
- Known gap in the `/permissions` text above: it covers judges turned off with `--disable_judge` only. With `--local_only` and the local judge unreachable, a protected command in **Edit + system commands** also runs with no model review and no question, and the panel still shows the reviewed text, because it does not probe the judge.
- `/permissions` no longer says a protected command is reviewed when it is not. With the automatic judges off (`--disable_judge`) it now shows `Sandboxed, not reviewed` for a project in **Edit + system commands**, where such a command runs with no model review and no question, or that you approve each command, or that Codex still reviews every command when the project's command review is Codex or both. The `--disable_judge` help and the guides say the same. Only the text changed; nothing about when commands run or are reviewed did.
- The approve button of **Run this command?** now reads **Allow this command** instead of **Allow for this task**, because one answer releases only that one exact command and tare may ask again for the next one. The file-access question keeps **Allow for this task**, which does cover the task and its corrections. The daily-use guide, in English and Portuguese, says the same.
- **Run this command?** (asked when no automatic judge can review a protected command) no longer expires after the command's review window (60 seconds by default) and no longer spends the turn's time: while it waits, the asking session's time limit stops, and so do the conversation's when its implementer asks and the elapsed time the console shows; the saved deadlines move by the same wait (`answer_wait_seconds`). Only your answer, cancelling the turn or the asking process ending closes it. You approve the command, not its deadline: after a yes tare takes the command again and runs it only if everything but the deadline (command, folder, environment, inputs, context, policy, grant, binding) is unchanged, under a fresh short window, so the authorization stays short-lived. Machine reviews and YOLO keep their windows. The question's `expires` is now a 10-second lease its asker renews, so a question whose asker died leaves the console; the review record names the assessed action (`action_sha256`) and the receipt keeps the classifier's usage when the executed action's hash differs only by its renewed deadline.
- The model button above the input box also keeps the model's name while a turn runs in a new conversation, where it used to fall back to "Model". The `/guidance` panel tests now wait until the panel shows the highlighted text, after one of them failed on a busy CI runner and held back a release.
- `/guidance` keeps the text you had selected when the startup reading lands. Refilling the list highlighted its first text a moment later, which could move the selection to the top; a CI run caught it.
- Diffs now have colours: in the Files pane (F8, `d` on a file, and a commit from `h`) and in the `/guidance` before and after view, removed lines are red, added lines green and hunk headers bold, in the colours of the theme you use. Text such as `<permissions instructions>` or `[x]` is shown as written. The `/guidance` before and after view can still only be read, not edited.
- While the **Implement this plan?** dialog (or the edit-access question it replaces with **Go straight on**) waits for your answer, the turn's time no longer runs: its time limit stops, so a late answer is still honoured and the time left afterwards is what it was when the question was asked; only cancelling the turn ends the wait. The conversation's saved deadline moves by the same wait, so the implementer is funded from the time that was left, and the waited seconds are recorded in the session (`answer_wait_seconds`). The status line shows "Waiting for your answer · the turn's time is paused" and its elapsed count stops. Before, a turn with a time limit spent the minutes you took to read the plan, and the wait itself could run out with nothing implemented. "Run this command?" is a separate wait and keeps its own review window (60 seconds by default).
- `/permissions`, **Before implementing**, now also has a default of yours for every project: **My default, every project** (**Show me the plan and ask** until you choose, or **Go straight on**), kept in `<storage>/console/project-permissions/defaults.json`. The project's own choice gains **Use my default**, which names what your default is now and is what a project without a choice shows; a project's own **Show me the plan and ask** or **Go straight on** still wins over your default. So someone who prefers to go straight on sets it once and a new project follows. The value is read when a plan is about to be implemented, so it reaches open conversations too.
- In the TUI, a plan is now shown before it is implemented. When a delivery reaches implementation, an **Implement this plan?** dialog shows the planner's whole plan (summary, steps, files, checks, what it must achieve and what the planner left uncertain), even in a project that already allows edits, and waits for **Implement this plan**, **Change the plan** or **Deny**; when the files also need edit access the same dialog asks for it, so there is one question, not two. **Change the plan** starts no implementer: the coordinator is told, with the line you typed, and asks the planner for a revised plan, which is shown again. An answer is remembered for that plan, so corrections under the same plan do not ask again. `/permissions` gains **Before implementing**: **Show me the plan and ask** (the default) or **Go straight on**, which behaves exactly as before. `tare serve` and headless runs are unchanged. The coordinator's guidance (version 16) names that dialog as the approval and tells the coordinator never to say a plan was approved.
- The working line above the input box now repeats the top status line exactly (elapsed time, who is working, its model, reasoning and the state of the call), so it names the planner, implementer or auditor when one of them is the one working, and the model that is really running instead of the model button's label. It is still empty when nothing is running.
- While a conversation is running, the row just above the input box now shows the working spinner with the model in use and its role ("⠋ Claude Sonnet 5.5 · coordinator"), where your eyes are; before, the spinner was only in the status line at the top. The row is empty when nothing is running, and the top line keeps its spinner and status text.
- The model button above the input box keeps showing the model's name while a turn starts; it used to switch to "Reading saved model…" for a few seconds, which the wider button made visible.
- The model button above the input box now shows the whole model name: it kept the width of its first label ("Model ▾") and cut the name of the model that loaded after it. It grows with the name, up to 65% of the row, and a name longer than that ends in "…" instead of being cut mid-word.
- `/guidance` variables: a Work delivery whose inference profile names no model no longer fails while filling `<model id>`; the name is left as written, as for any value the call cannot know.
- `/guidance`, Context: Claude Code's model block is no longer left out when Context is on, because it also gives the model's knowledge cutoff, which tare cannot fill; and Context's default text now carries, in tare's words, the caution about downloaded files that Claude Code's environment block gave.
- `/guidance` gains common texts and variables. A variable is a name and a text used as `<name>` in any text you can edit: tare fills the built-in ones (`<date>`, `<local time>`, `<OS version>`, `<working directory>`, `<model id>`, `<model name>`) on each turn, and you create your own. A common text is written once and added to the end of the system text of each new session, for every CLI and API route; sessions freeze it with its sha256. The built-in one, Context (today's date and the model), is off by default; while it is on, a session that carries it lets Claude Code leave out its environment, model and date blocks and Codex its environment block (where checked), and calls outside a session keep the CLI's own blocks, so none loses them without Context in their place. AGY's two matching blocks cannot be left out. With nothing turned on and no variable used, a session sends the same system text as before.
- tare now leaves Codex's skills list out by default: every Codex call carried the list of the skills installed on the machine (about 16,000 characters on the owner's), which the model cannot open because tare turns Codex's tools off. It is left out only on a Codex version where the startup reading checked that Codex really does; elsewhere it is still sent and `/guidance` says why. In `/guidance` the block is marked T, the before and after view shows what is left out, "Vendor's default" sends it again and "tare's default" leaves it out again; your own choice for the block always wins, and Reset everything goes back to tare's defaults.
- `/guidance`: the startup reading of what each CLI adds now runs before the provider quota refresh. In one real start the quota refresh took three minutes and the panel waited behind it; with the new order the reading was stored 32 seconds after the start.
- `/guidance` is easier to use. Its list is in groups (tare's role guidance, tare's protocol texts, Claude Code, Codex, AGY), each under a heading that cannot be selected, and each CLI's blocks are listed in the order they are sent. A changed text is marked as the Files pane marks a changed file: its name in colour and a bold letter, M edited, D removed, C default changed under your edit, U new; the first line gives the key. When the panel is opened while the startup reading is still running, each CLI group says it is being read and fills in by itself when the reading lands, keeping the selection and any text not saved yet; before, the CLI blocks appeared only when the panel was opened again. A block missing from the newest reading stays listed in grey, with when and on which CLI version it was last seen, and keeps its controls: Claude Code's reminder of the tokens left comes and goes between calls.

The panel says which version each kind of reading came from and when. The Codex reading without tokens now matches a real call (it lists the installed skills). - A release published by hand with `publish_product.py --here` is now created as a draft, and the publisher says how to sign it with the recovery key and publish it. It used to go public without `bundle.zip.sig`, and installed copies, which now take only signed releases, skipped it without saying anything.
- `scripts/ops/release_signing_key.py` now refuses to run when the release signing key is already set, unless you pass `--replace`: running it again replaced the CI key at once, and installed copies would then refuse every new release until one was signed by hand with the recovery key. Its help and ADR-075 now say that every key replacement needs the old recovery key.

- The publisher's test of who may publish no longer inherits `GITHUB_OUTPUT` from the CI runner: it failed there with `KeyError: 'tag'` and would have written into the test job's own outputs.
